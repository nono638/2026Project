Writeup

Project writeup · CUNY SPS, Spring 2026

RAGBench started as a question that seemed easy enough to measure: does a smarter Retrieval-Augmented Generation strategy actually compensate for using a smaller language model? Six BSODs, three revisions of the scorer validation, two full strategy × model factorials, and one painful realisation about uncollected provenance later, the answer is “mostly no — but the experiment that taught us that needed more honesty about its own limits than the first dashboard suggested.”

Why RAGBench

In plain language: a Retrieval-Augmented Generation system is a chatbot that looks things up in a corpus before answering, instead of relying purely on what its language model memorised during training. A dozen design choices go into one — how the corpus is split into passages, which model retrieves them, which model writes the answer, how the prompt is structured, whether the system tries a second pass if the first looks bad. Small changes in any single component can swing answer quality by tens of percent, but published claims about which choices matter usually compare apples to oranges across studies. The hard part isn’t running one configuration; it’s comparing many fairly enough that the differences mean something.

The RAG literature is loud about strategy choice. Every few weeks a new paper or blog post argues that some flavour of self-critique, query reformulation, or adaptive routing unlocks meaningful quality on a smaller, cheaper model. The claims are plausible — small models hallucinate more, and an extra LLM pass to verify or refine should help. But the numbers cited are usually on different datasets, with different models, against different retrievers, scored by different judges. There’s nowhere obvious to look and ask: under controlled conditions, on a shared question set, with everything else held constant, how big is the strategy effect actually?

RAGBench is a configurable harness that tries to answer that question for one shared question set (HotpotQA), one held- constant embedder per experiment, one chunker per experiment, and a panel of LLM judges that we first validated against gold-standard metrics. What’s new isn’t the strategies themselves — each is from a published 2024–2025 paper — it’s the comparison protocol: every strategy run on every model on the same questions, with the same chunker and embedder, scored by judges validated against ground truth on a separate set first. The approach should work because the only thing varying inside one experiment is the axis the experiment names. It runs the full cartesian product of (chunker × embedder × strategy × LLM) configurations specified on the command line and writes per-row results to a CSV that downstream analysis reads. The codebase is on GitHub; it’s very much a personal research project, not yet something I’d ask a stranger to install and trust.

Who benefits from this: developers picking a RAG architecture under a fixed compute or money budget, researchers needing a sanity check before citing LLM-as-judge correlations, and students trying to understand which RAG knobs actually move the needle versus which sound clever but don’t. If the findings replicate elsewhere, the practical consequence is permission to default to the boring choice — plain retrieval on a mid-size model — and to spend the saved engineering effort somewhere it’s actually measurable, like prompt design or the choice of dataset.

What we set out to test

Three working hypotheses going in. I’ll mark each with what the data eventually said.

  1. H1. A clever RAG strategy on a small language model will frequently beat plain NaiveRAG on a larger model. — Result: mostly false, and within noise where it’s not. Naive (4.34 [4.30, 4.39]), Multi-Query (4.33 [4.29, 4.38]), and Corrective (4.27 [4.22, 4.32]) have overlapping 95% CIs — they’re a 3-way tie, not three distinct ranks. The “Strategy Beats Size” chart finds upset cases but the average delta (+0.08 to +0.10) is comparable to the CI half-widths it’s claiming to exceed. Self-RAG (2.99) and Adaptive (3.59) actively hurt every model with no CI overlap with the top cluster — those effects are real.
  2. H2. Quality will scale roughly monotonically with model size. — Result: monotonic at the bottom; flat with overlapping CIs at the top. qwen3.5:0.8B (3.27 [3.20, 3.35]) is clearly weakest. From 2B upward, adjacent sizes start overlapping. The earlier claim that “4B beats 9B in both experiments” doesn’t survive a CI test in Experiment 1 (qwen3.5:4B 4.05 [3.98, 4.12] vs qwen3.5:9B 4.03 [3.96, 4.09] overlap heavily). In Experiment 2 the comparison flips and 4B (4.58 [4.53, 4.62]) does cleanly beat 9B (4.45 [4.40, 4.49]) — likely because Exp 2 holds strategy constant at NaiveRAG and so the comparison is less noisy.
  3. H3. Chunker choice will interact meaningfully with model size — better chunking will rescue smaller models. — Result: partially false, but with a major asterisk. Fixed (4.32 [4.26, 4.38]) vs sentence (4.11 [4.04, 4.18]) is the only chunker pair with non-overlapping CIs. Fixed / recursive / semantic CIs all overlap. Crucially, Experiment 2 ran against mxbai-embed-large (512-token window), and two of the four chunkers (fixed and semantic) routinely produce chunks larger than that — their content was silently truncated to 512 tokens before embedding. So the rankings above describe behaviour under client-side truncation, not the chunkers as designed. “Sentence is worse” survives that caveat (sentence chunks fit cleanly, so the comparison favours truncation-free chunkers and sentence still lost); the 3-way tie at the top is genuinely unknown without an un-truncated re-run. See the prominent caveat at the top of the Experiment 2 page.

How we’d know if this is working (the midterm-vs-final-exam question): a successful version of this project would clear three bars. (1) Effects survive replication on at least one second dataset beyond HotpotQA — SQuAD 2.0 is wired up but unused, and a long-form domain corpus would be a stronger second test. (2) Confidence intervals are tight enough to distinguish the small inter-strategy gaps observed here — we have CIs at the headline level now, but the Naive / Multi-Query / Corrective tie isn’t something we can crack open without either many more questions per cell or deterministic generation. (3) Per-row provenance is complete enough that an external reader can reproduce the analysis from the CSVs alone — phase 1 of that work shipped (prompts, intent labels, call counts going forward); the audit table below names the rest. Today we have a partial (2) and a partial (3); (1) is on the backlog. That’s the rubric.

Headline findings, cross-experiment

Pulled together from the two experiment dashboards.

  • Strategy effects are mostly within CI; two strategies clearly hurt. Naive / Multi-Query / Corrective are a 3-way tie at 95% (CIs overlap by 0.02–0.10 points). Self-RAG and Adaptive sit 0.7–1.4 points lower with no CI overlap — those negative results are the most defensible findings in the dataset.
  • Model size effects are largest at the bottom of the range. 0.8B is cleanly below everything else in both experiments. Above 2B the CIs start overlapping, and whether 4B cleanly beats 9B depends on which experiment’s holding- constant assumptions you trust more (Exp 2 says yes with non-overlapping CIs; Exp 1 says they’re indistinguishable).
  • Chunker choice has one real signal — under a major caveat. Sentence chunking is genuinely worse than fixed (~0.20 quality points below, CIs don’t overlap). The other three chunkers (fixed, recursive, semantic) are indistinguishable. But Experiment 2 ran against mxbai-embed-large (512-token window) and two of the four chunkers (fixed and semantic) had their chunks silently truncated to fit, so the rankings describe behaviour under truncation rather than the chunkers as designed. The “avoid sentence” finding survives that caveat; the 3-way tie at the top doesn’t. See the Experiment 2 page’s caveat callout for the details.
  • LLM judges agree when they’re contemporaneous. Experiment 0 v3 ran 9 judges on 500 questions; cross-provider Pearson against gold F1 was 0.55–0.60 for current-generation models (GPT-5.4, Claude Sonnet 4.6) and dropped 30–45% for older variants of the same families. Model version drift dominates provider differences — an under-appreciated property of the LLM-as-judge approach.
  • The winning configurations are boring. Experiment 1 winner: NaiveRAG × qwen3.5:4B (4.59 [4.49, 4.68], 59% exact match). Experiment 2 winner: fixed-size chunker × qwen3.5:4B (4.65 [4.55, 4.73], 74% exact match). No clever strategy, no clever chunker, mid-size model. The interesting content is in the absence of the expected effects, not in the rankings themselves.

The technical reality: the laptop kept crashing

The biggest non-research problem in the whole project was that the laptop running everything kept crashing. Over three days in mid-May the machine blue-screened six times while in the middle of long batch experiments. Each crash forced a reboot and lost whatever the experiment was working on at that second. The cause turned out to be a known stability problem with the laptop’s graphics card and its driver when running language models for long stretches — not a bug in RAGBench’s code, but very much our problem to work around.

Solving it took five layers of fixes stacked on top of each other: slowing down the rate at which RAGBench called the language model, tuning Ollama (the local model server) to use less aggressive defaults, raising some Windows timeout settings that were too short for long model-generation kernels, saving progress to disk after every single row so a crash cost at most one row of work, and finally wrapping the whole experiment in a supervisor program that automatically restarts and resumes the run after the laptop reboots. With all five in place, the last 300 rows of Experiment 1 finished in 46 minutes on a single uninterrupted attempt — after weeks of fighting the same section of the matrix.

The broader lesson: on consumer hardware, don’t trust that your machine will stay up for the whole duration of a long ML experiment. Write the experiment as if it will be interrupted, because eventually it will.

What we got wrong: Experiment 0’s three revisions

Experiment 0’s job was to pick the LLM judge for Experiments 1 and 2. The first version was sound enough to answer the literal question asked but had five methodological oversights that only surfaced under post-analysis. The reason there are three versions of Experiment 0 on this site is that we kept catching them and fixing them.

v1: the first end-to-end run

50 HotpotQA questions sampled proportionally across difficulties, scored by 6 LLM judges. Headline conclusion: use Claude Sonnet as the primary scorer. The five oversights:

  1. Pipeline observability was absent. We generated answers but didn’t record which chunks were retrieved, what context was assembled, or what the LLM actually saw. When a row failed, “why?” was guesswork.
  2. The scorer judged against information the LLM never received. We passed the full source document to the judge for the faithfulness rating, but the answering model only saw the small subset of retrieved chunks. A hallucinated detail that happened to appear elsewhere in the document scored as “faithful.”
  3. No reranker. v1 used raw hybrid retrieval (BM25 + dense with RRF fusion) with no cross-encoder reranker, which meant we validated our scorers on a different pipeline configuration than the one Experiments 1 and 2 would use.
  4. Ceiling effect. 50 questions proportionally sampled meant ~74% exact match. With ~13 wrong answers there wasn’t enough signal to discriminate between judges.
  5. No composite quality metric. We had BERTScore, F1, and judge ratings as independent signals but no way to ask “do all three agree this answer is good?” A judge that gave 5/5 to an answer with low BERTScore and low F1 had a blind spot we couldn’t see.

v2: corrections, but still single-judge thinking

150 medium+hard questions (eliminating the ceiling effect), BGE reranker added, scorer fed the actual context the LLM received, pipeline diagnostics captured. Conclusion stood (Sonnet wins) but with the caveat that we were still evaluating one judge at a time against gold metrics. The insight that judges should be evaluated as a panel, cross-validating each other, hadn’t landed yet.

v3: the version-drift discovery

500 questions, 9 judges spanning 3 providers and 4 Claude generations. Two things emerged that weren’t in the original plan:

  • Model version drift dominates provider differences. Claude Sonnet 4 hit r=0.40 against gold F1; Claude Sonnet 4.6, same provider eight months later, hit r=0.58 — a 45% relative improvement on identical answers. A spot-check of Opus 4 vs Opus 4.7 showed the same pattern. Within-provider version differences turned out to exceed cross-provider differences, which has consequences for anyone using LLM-as-judge: you can’t cite an old judge model’s correlation number and assume the current version of the same family behaves the same.
  • GPT-5.4 Mini is the best value judge. r=0.55 against gold F1, $0.0015 per call, no version-drift penalty. The final v3 conclusion changed the Experiment 1 / 2 panel from “Claude Sonnet” to “Claude Haiku 4.5 + GPT-5.4 Mini”: cross-provider, both current-generation, ~$32 total budget across both full experiments.

The v1 conclusion on the website is annotated as superseded by v3 rather than rewritten, so the methodological evolution is visible to a reader.

What we got wrong: Experiments 1 and 2

By the time Experiments 1 and 2 ran, we’d learned quite a bit from Experiment 0’s revisions: we were now capturing what the LLM actually saw, scoring against that, using a validated cross-provider judge panel, and running on a real factorial design. The dashboards look polished. They are not as scientifically robust as they look.

The big oversight wasn’t about what we measured but what we wrote down per row. The CSV captured the final answer text, the final context sent to the LLM, total strategy latency, and gold-vs-RAG metrics — plenty for headline rankings. What it didn’t capture:

  • The number of LLM calls per row — only a process-wide running total in the heartbeat log.
  • The branch path taken by Corrective (did reformulation fire?) or Adaptive (which sub-path did the classifier pick?).
  • The intermediate LLM outputs (the “relevant”/“irrelevant” ratings inside Corrective, the reformulated query Multi-Query produced, the classifier verdict Adaptive returned). These drive branch decisions and become inputs to later prompts — missing them means missing the per-row substituted prompts for every call after the first.
  • The code SHA at generation time, so an analyst could pin which version of src/strategies/ produced a given row.

The prompt templates are version-controlled in src/strategies/*.py, so the prompt shape for every call is recoverable from source. What isn’t recoverable per row is the substituted content for any call whose input came from a prior LLM output. For NaiveRAG that’s fully recoverable (one fixed template, one chat call); for the other four strategies it isn’t.

That gap matters most for CorrectiveRAG and AdaptiveRAG, which are precisely the strategies whose value depends on conditional behaviour. Without recording the conditional outcomes we can’t do the fine-grained error analysis that distinguishes “strategy didn’t help” from “strategy helped on the rows where its second pass actually fired.” That’s the difference between a publishable experiment and a working demo, and we should own it openly.

Phase 1 of the fix shipped: a per-row trace (begin_row / end_row / record_complete) wraps every OllamaLLM.generate call, every strategy now tags its calls with an intent label (rate_relevance, reformulate_query, classify_complexity, etc.), and the runner writes the full per-call trace to a sidecar traces.jsonl alongside events.jsonl. Seven new CSV columns (n_llm_calls, llm_call_intents, final_prompt, prompts_source, code_sha, llm_num_predict, llm_keep_alive) carry the summary. Historical rows have been schema-aligned via a backfill script; NaiveRAG rows have their final_prompt reconstructed byte-deterministically, multi-step strategy rows are tagged but not fabricated.

Stochastic generation: the reproducibility cost

The other reason Experiments 0–2 are less reproducible than they should be: the runner used Ollama’s default generation parameters, which include temperature ≈ 0.8 and no seed. The same row, if re-run today, would produce a different answer — and possibly a different LLM judgement of it, and possibly a different branch path in Corrective or Adaptive.

That means row-level reproducibility is gone. Aggregate statistics (mean F1 over 200 questions, strategy × model rankings) remain meaningful in expectation, but their variance carries unnecessary stochastic-generation noise. The 0.07-point gap between Naive and Corrective in Experiment 1, and the 0.20-point chunker spread in Experiment 2, are both within the noise band that a temperature = 0 + fixed-seed regime would eliminate. We don’t know how much of that “within noise” is real indistinguishability vs sampling variance until we re-run with deterministic generation.

This is one line of options in OllamaLLM.generate and a few CSV columns to stamp it per row; the new per-row instrumentation can carry it without further changes. Phase 2 work.

The full audit: uncollected details, severity-ranked

The prose above sketched the gaps in narrative form. This is the comprehensive list, ordered by how much each gap limits interpretability of Experiments 0–2. None of these invalidate the headline findings; they constrain how finely the data can be sliced, audited, or reproduced. Items 1, 2, and 3 are the practical limit to how scientific the existing data can be made retroactively; for the next experiment, items 1, 2, 4, 6, and 7 are the right batch to add together.

Most severe · affects every row in every experiment

Stochastic generation without a fixed seed

Generation parameters were not set explicitly — the runner used Ollama’s defaults, which include temperature ≈ 0.8 and no seed. That means a given row, if re-run today, would produce a different answer (and possibly a different LLM judgement, and possibly a different branch path in CorrectiveRAG / AdaptiveRAG). Row-level reproducibility is therefore not what a research benchmark should provide. Aggregate statistics (mean F1 over 200 questions, strategy × model rankings) remain meaningful in expectation, but their variance is partly stochastic-generation noise that a temperature = 0 + fixed-seed regime would eliminate. The fix is one line of options in OllamaLLM.generate; a principled fix also stamps temperature, top_p, top_k, and seed per row, which the new instrumentation can carry without further changes.

How far is this from public-ready?

Honestly, a fair amount. RAGBench is a personal research project I’d be comfortable showing to a hiring manager or to a faculty advisor; I’d not be comfortable having a stranger cite the numbers as if they were a benchmark on the order of MTEB or HELM. The distance from here to “cite-able benchmark” is roughly:

  • Strict reproducibility. Fix temperature=0 + seed, pin every dependency version, stamp library + Ollama versions per row. Without this no number can be exactly replicated.
  • More than one dataset. Everything here is HotpotQA. The conclusions need to be replicated on at least one factoid dataset (SQuAD 2.0 is wired up but unused) and one long-form / domain- specific corpus before they generalise.
  • More than one hardware platform. All the timing data is from one 5090 Laptop on one Windows install. Latency comparisons would shift on a server-class GPU, and the BSOD story is specifically a 5090 driver issue.
  • Cost measurement, not estimation. Currently cost is estimated from string length × ~4. Per-call prompt_tokens/completion_tokens from Ollama’s /api/chat response turns that into measurement; on the API side we have the actual usage figures from the SDKs already.
  • Per-row provenance for everything in the audit table. Phase 1 fixed prompts + call counts; Phase 2 needs generation params, strategy hyperparameters, branch outcomes, token counts, per-chunk retrieval scores.
  • Documentation for outside users. The README is honest about what works on the author’s machine. It’s not a Quickstart that would land cleanly on a fresh install elsewhere — the Ollama setup, the model downloads, the API keys, the Windows-specific stability scripts, and the assumption of an RTX-class GPU would all need spelling out.
  • Statistical analysis beyond the dashboards. The visualisations summarise; they don’t prove anything. A proper writeup would include an ANOVA on the strategy × model design, a regression isolating the main effects, and a discussion of where the negative results are bounded by sample size.
  • Test coverage for edge cases. 691 tests pass today, but they cover happy paths plus the failures we’ve already debugged. Network partition during retrieval, Ollama runner mid-call crash, malformed strategy output, judge API rate limit during a long run — some of these are handled in code, none of them are systematically tested.

That’s probably another month of focused work to close. The good news: most of it is mechanical, not conceptual. The hard part — designing the experiments, picking the judges, surviving the 5090 — is largely behind us.

What’s next

  • Set temperature=0 and a per-row seed in OllamaLLM.generate, stamp both per row. Re-run a subset (say, 10 questions × full matrix) to estimate how much of the inter-strategy noise is stochastic vs systematic.
  • Expose strategy hyperparameters (min_relevant_chunks, n_alt_queries) as Python properties instead of hardcoded constants, and stamp them per row.
  • Pull Ollama’s eval_count / prompt_eval_count into the per-call trace records; surface per-row token totals in the CSV.
  • Run Experiment 1 again with the new instrumentation, so a clean apples-to-apples comparison exists between “reconstructed-minimal” and “recorded” regimes.
  • Decide whether to publish at all, or to leave RAGBench as a personal infrastructure project and use the lessons (logging-first instrumentation, BSOD-resilient runners, transparent retrospective) on the next thing.
