RAGBench

A configurable evaluation pipeline for Retrieval-Augmented Generation

RAGBench runs the full cartesian product of RAG configurations (chunker × embedder × strategy × language model), scores the results with LLM judges, and identifies optimal configurations for different constraints.

What is RAG?

Retrieval-Augmented Generation (RAG) is the dominant pattern for grounding language models in external knowledge. Instead of relying solely on what the model memorized during training, a RAG system retrieves relevant passages from a corpus — documentation, papers, internal wikis — and feeds them to the model alongside the question. The model then generates an answer grounded in the retrieved context.

That means a RAG pipeline has many moving parts, each of which independently affects answer quality: how the corpus is chunked, how passages are retrieved, how retrieval results are reranked, how the prompt is constructed, and which language model produces the final answer. Small changes in any one component can swing accuracy by double-digit percentages.

For a deeper look: NVIDIA: What is RAG? (illustrated overview with multi-stage architecture diagram) · LangChain — RAG from Scratch (in-depth notebooks & diagrams covering query translation, routing, indexing, retrieval, and generation)

Foundational reading: Lewis et al. 2020 (the original RAG paper) · Wikipedia overview · Hugging Face RAG docs

What is RAGBench?

RAGBench is a configurable harness for measuring how those moving parts affect quality. It runs the full cartesian product of RAG configurations (chunker × embedder × reranker × strategy × LLM) over a shared question set, scores every answer with both automated metrics (BERTScore, F1, exact-match against gold answers) and a panel of LLM judges rating faithfulness, relevance, and conciseness, then compares results across configurations to identify best-per-cost frontiers.

The diagram below shows one row of the pipeline: a question and its source documents flow through the RAG configuration on top, the gold answer is held out as ground truth on the bottom, and both objective metrics and LLM judges score the result.

Inside that pink RAG Pipeline box are five components. Any of them can be a test axis depending on the experiment — Experiment 1 varies the RAG strategy, Experiment 2 varies the chunker, and so on — while the others are held constant within each experiment so the effect being measured is not confounded. Indexing happens once per corpus on top; every query traverses the bottom row.

RAG Strategies in This Study

Five strategies, each adding a different layer of intelligence between the user’s question and the language model’s answer. The first is the baseline; the rest each spend extra LLM calls to compensate for retrieval or reasoning gaps.

NaiveRAG
Retrieve, then answer. One round of hybrid retrieval; the top-5 chunks are concatenated into the prompt; one LLM call produces the answer. The control condition every other strategy is measured against.
LLM calls per question: 1 · Tradeoff: cheap and predictable, no recovery from bad retrieval.
SelfRAG
Retrieve, critique, answer. After retrieval, the model is prompted to judge whether the retrieved context is sufficient. If not, it answers from parametric knowledge instead. Trades 1 extra LLM call for awareness of its own retrieval failures.
LLM calls per question: 2 · Tradeoff: handles retrieval misses, but adds latency on every query.
MultiQueryRAG
Reformulate, then retrieve N times. The original question is rewritten into 3 paraphrases; each runs a retrieval pass; the union of chunks is deduplicated and answered against. Helps when the question’s wording happens to mismatch the corpus vocabulary.
LLM calls per question: ~5 (1 reformulation + ~3 retrievals + 1 answer) · Tradeoff: better recall, more chunks to sort through.
CorrectiveRAG
Retrieve, filter chunk-by-chunk, optionally retry. Every retrieved chunk gets a per-chunk relevance rating from the LLM. If fewer than 2 chunks survive the filter, the query is reformulated and a second retrieval round runs. Based on Shi et al. 2024. Branchy — one of the strategies where logging matters most.
LLM calls per question: ~6–13 (1 per retrieved chunk + optional reformulation + final answer) · Tradeoff: precise context, high cost on long retrieval lists.
AdaptiveRAG
Classify the question, then pick a strategy. The model first labels the question (factoid vs reasoning vs multi-hop), then routes to a strategy matched to that type. Tries to give each question the right amount of pipeline, instead of paying the heaviest cost on every query.
LLM calls per question: variable (1 classifier + however many calls the chosen sub-strategy uses) · Tradeoff: best amortized cost; harder to reason about per-row behaviour.

The per-row substituted prompts as actually sent, the branch path taken, and the exact LLM-call count were not stamped on the rows that produced Experiments 1 and 2 — an experimental-design oversight we’re owning rather than hiding. The prompt templates themselves are version-controlled in src/strategies/*.py, so the prompt shape is recoverable; what isn’t recoverable per row is the substituted content for any call whose input came from a prior LLM output. Historical CSVs have been backfilled where possible (NaiveRAG’s substituted prompt is byte-deterministic and has been reconstructed from the recorded context + question; multi-step strategies are schema-tagged but not fabricated). New runs from now on capture the full trace per row. See Methodology » Logging Gaps & What We’re Fixing for the audit and the fix.

Experiment 0: Which LLM Judge Tracks Truth?

Frontier-class judges converge — version matters more than provider.

500 HotpotQA questions. 9 LLM judges. GPT-5.4 leads at r = 0.605, with Claude Sonnet 4.6 (0.575) and GPT-5.4 Mini (0.553) close behind. Older Claude versions (Sonnet 4, Opus 4) score ~30% lower than current Sonnet 4.6 — model version drift outweighs provider differences.

Key Findings

From Experiment 0v3 — 500 HotpotQA questions scored by 9 LLM judges (3 Gemini + 4 Claude + 2 OpenAI).

GPT-5.4 is the most accurate LLM judge

Highest correlation with gold F1 (r=0.605) at n=500. Sonnet 4.6 (0.575) and GPT-5.4 Mini (0.553) follow.

Model version dominates provider differences

Claude Sonnet jumped from r=0.397 (4) → 0.575 (4.6) — a ~45% relative gain. Same provider, different generation.

GPT-5.4 Mini is the best value

r=0.553 at $0.0015/call — most accurate among cheap judges, and cross-validates with Sonnet 4.6 (r=0.720).

76% exact match on HotpotQA — answer quality is solid

Retrieval failures at 14%, generation failures at 10%. Pipeline works well out of the box.
