Methodology

Pipeline Overview

RAGBench evaluates RAG configurations by running each query through every combination of five independent axes, scoring the outputs, and comparing them against gold-standard answers when available. The diagram below shows the RAG pipeline itself: indexing happens once per corpus on top, every query traverses the bottom row. Magenta boxes are the test axes that vary across experiments; gray boxes are passive infrastructure or held constant.

The Five Axes

Each experiment varies one or two axes while holding the others constant, isolating the effect of each design decision.

Chunker

How documents are split into passages for retrieval. Options: fixed-size (512 tokens), recursive (500/100 overlap), sentence-boundary, and semantic (embedding-aware splits).

Embedder

How text chunks become vector representations for similarity search. Embedder choice is held constant within each experiment but changed once across the project timeline, so different experiments use different embedders.

  • Experiment 2 (run before the 2026-05-13 switch): mxbai-embed-large via Ollama — 512-token context.
  • Experiment 1 & Experiment 0 v3 (post-switch): embeddinggemma:300m via Ollama — 2048-token context, 768-dim output, Apache 2.0, ~300 MB on disk.

The switch was a methodological response to a chunking-vs-embedder conflict surfaced during the first Experiment 2 run: the FixedSizeChunker(500 words) and SemanticChunker configurations triggered hundreds of HTTP 400s because their chunks (~700 tokens and up) overflowed mxbai’s 512-token window. Setting Ollama’s server-side truncate=true didn’t help on the current Ollama version, leaving client-side truncation as the only fix. Truncating chunks to fit a small embedder isn’t a fair test of chunkers — it silently discards the tail of every oversized chunk before similarity is computed, penalising any strategy that prefers larger units. The replacement is EmbeddingGemma 300M: a text-only encoder distilled from Gemma 3 with a 2K-token context, released under Apache 2.0 by Google, well-rated on MTEB at the sub-1B size class, and small enough that it co-resides comfortably with the 9B generation models on a 24 GB GPU.

The earlier mxbai-embed-large data is preserved in Experiment 2’s archive but no longer drives new generation runs. Comparisons that span both experiments should treat the embedder as a known difference, not a held-constant variable.

Reranker

An optional second-pass ranker that re-scores retrieved chunks before they reach the LLM, improving precision at the cost of latency. Options: BGE reranker (cross-encoder), MiniLM (lightweight), or none. Experiment 0 uses BGE; Experiments 1 and 2 run without a reranker to isolate other variables.

Strategy

How retrieved context is used to generate answers. Five strategies tested: NaiveRAG (single retrieval), SelfRAG (self-critique loop), CorrectiveRAG (retrieval validation), AdaptiveRAG (complexity routing), and MultiQueryRAG (query expansion).

Model

Which language model generates the final answer. Tested in Experiments 1 and 2: Qwen 3.5 small tier (0.8B, 2B, 4B, 9B) plus Gemma 4 e-tier (e2b ≈ 2.3B effective, e4b ≈ 4.5B effective) for the cross-family comparison in Experiment 1. All run locally via Ollama, GGUF Q4_K_M / Q8_0 quantisations as Ollama’s default tags ship them.

Evaluation Approach

RAGBench uses dual evaluation to assess answer quality from two perspectives:

Intrinsic evaluation (always available): An LLM judge scores each answer on faithfulness, relevance, and conciseness against the retrieved context. No external reference data needed.

Extrinsic evaluation (when gold data exists): Answers are compared against known-correct reference answers using BERTScore and token-level F1. This enables scorer validation — Experiment 0 exists specifically to validate the LLM-as-judge approach against gold-standard metrics.

Scorer Selection

Experiment 0 ran 500 HotpotQA questions through ten LLM judges (3 Gemini, 5 Claude, 2 OpenAI) and correlated each judge's quality scores against the gold metrics (BERTScore F1, token-level F1). The headline result: GPT-5.4 led at r=0.605, with Claude Sonnet 4.6 (0.575) and GPT-5.4 Mini (0.553) close behind.

The unexpected finding was model version drift. Claude Sonnet 4 (May 2025) hit r=0.397; Claude Sonnet 4.6 (the same provider, eight months later) hit r=0.575 — a ~45% relative improvement on identical answers. A spot-check of Claude Opus 4.7 on a 66-row subset showed the same effect: Opus 4 scored r=0.452 on those rows, Opus 4.7 scored r=0.698. Within-provider version differences turned out to exceed cross-provider differences.

Final scorer panel for Experiments 1 and 2: Claude Haiku 4.5 (r=0.450, $0.002/call) and GPT-5.4 Mini (r=0.553, $0.0015/call). Both are the latest generation of their respective family lines (no version-drift penalty), both sit in the cheap tier, and they sit in different capability tiers across different providers — yielding a more genuinely independent cross-validation than a top-tier same-tier pair would. Total estimated cost across both full experiments (Exp 1 = 5 strategies × 6 models × 200 questions, Exp 2 = 4 chunkers × 4 models × 200 questions, ~9,200 rows per judge): ~$32. Sonnet 4.6 was considered as the primary (r=0.575) but at 5× the per-call cost it would have raised the panel total to ~$106 for ~22% better correlation — not worth it for relative-ranking research questions where judge consistency matters more than absolute gold-correlation.

Dataset

The primary corpus is HotpotQA — 113K multi-hop Wikipedia question-answer pairs with gold-standard answers and difficulty labels (easy, medium, hard). Multi-hop questions require reasoning across multiple passages, making them a rigorous test of retrieval and generation quality.

Secondary: SQuAD 2.0 (simple factoid Q&A for easy-baseline calibration).

Logging Gaps & What We’re Fixing

Experiments 0 through 2 ran before RAGBench stamped per-row LLM provenance onto the dataset — a real instrumentation oversight that matters most for the branchy strategies (CorrectiveRAG, AdaptiveRAG, Self-RAG). What we recorded per row was the final answer text, the final context sent to the LLM, total strategy latency, and gold-vs-RAG metrics — plenty for headline results. What we did not record:

One thing that isn’t on the list below: the prompt templates. Those live in src/strategies/*.py (e.g.  RELEVANCE_PROMPT, REPHRASE_PROMPT, CLASSIFY_PROMPT, CRITIQUE_PROMPT), are version-controlled in git, and have not changed since the runs. So the prompt shape for every call is recoverable from the source. What’s missing per row is laid out below.

  • The literal substituted prompt strings as actually sent — including content that came from prior LLM outputs (the specific reformulated query Multi-Query produced for this row, the specific classifier verdict Adaptive returned, the per-chunk relevance ratings Corrective applied). For first-call-in-strategy prompts the substitution is deterministic given (template, retrieved chunks, query) and partially reconstructable; for any subsequent call whose input was a prior call’s output, the substituted string is gone.
  • The number of LLM calls per row — only the process-wide running total was snapshotted into the heartbeat log.
  • The branch path taken — for Corrective, whether reformulation fired; for Adaptive, which sub-path the classifier chose; for Self-RAG, whether the critique pass changed the answer.
  • The intermediate LLM outputs — the “relevant”/“irrelevant” ratings, the reformulated query text, the classifier’s output. These drive the branch decisions and become the next call’s prompt content, which is why item 1 lists them as the unrecoverable part of the substituted prompts.
  • The code SHA at generation time, so a later analyst can pin down which version of src/strategies/ produced a given row.

For NaiveRAG those omissions don’t much matter — the strategy has one fixed template, one chat call, and a fully deterministic substituted prompt. For the other four they matter quite a bit. CorrectiveRAG conditions a second retrieval pass on the outcome of N intermediate LLM ratings; without recording those ratings we can’t tell from a row whether it took the one-pass branch or the two-pass branch, which makes the cell unsuitable for the kind of fine-grained error analysis that distinguishes “strategy didn’t help” from “strategy helped on the rows where its second pass fired.” That’s the kind of gap that distinguishes a publishable experiment from a working demo, and we should own it openly rather than hide it behind a polished dashboard.

Going forward (Phase 1, shipped): the runner now opens a per-row trace before each strategy run; every OllamaLLM.generate records its intent, full prompt, response, and latency into that trace; at row end the trace is written to a sidecar traces.jsonl alongside raw_scores.csv and a compact summary is written to seven new CSV columns (n_llm_calls, llm_call_intents, final_prompt, prompts_source, code_sha, llm_num_predict, llm_keep_alive). New rows produced from this commit forward carry prompts_source = "recorded".

Backfill (shipped): historical rows have been tagged prompts_source = "reconstructed_minimal_2026-05-20". NaiveRAG rows have their final_prompt reconstructed deterministically from the byte-identical template + the recorded context_sent_to_llm. Multi-step strategy rows were not filled with fabricated prompts — the backfill stops at what we can prove. Anyone joining historical with new data should filter on prompts_source to keep the two regimes distinguishable.

Phase 2 (next): the strategies themselves should expose a hyperparameter dict (CorrectiveRAG’s “reformulate if fewer than 2 pass” threshold, Multi-Query’s “3 sub-queries” count), stamped per row. Per-call token counts via Ollama’s /api/chat stats would let us answer cost-vs-quality questions without estimating token counts from string length. Embedder calls deserve their own counter, separate from chat calls. See the audit table below for the full backlog.

Retrospective: Uncollected Details & Reproducibility Gaps

The Logging Gaps section above covers the per-row prompt and call-count omissions that Phase 1 has now fixed. This section is a wider audit of granular details that Experiments 0, 1, and 2 also did not record — honestly scoped, with severity, so the limitations of the existing data are visible to anyone reading the results rather than buried in the codebase.

Most severe · affects every row in every experiment

Stochastic generation without a fixed seed

Generation parameters were not set explicitly — the runner used Ollama’s defaults, which include temperature ≈ 0.8 and no seed. That means a given row, if re-run today, would produce a different answer (and possibly a different LLM judgement, and possibly a different branch path in CorrectiveRAG / AdaptiveRAG). Row-level reproducibility is therefore not what a research benchmark should provide. Aggregate statistics (mean F1 over 200 questions, strategy × model rankings) remain meaningful in expectation, but their variance is partly stochastic-generation noise that a temperature = 0 + fixed-seed regime would eliminate. The fix is one line of options in OllamaLLM.generate; a principled fix also stamps temperature, top_p, top_k, and seed per row, which the new instrumentation can carry without further changes.

The table below ranks the remaining gaps by how much they limit interpretability of Experiments 0–2. None of them invalidate the headline findings; they constrain how finely the data can be sliced, audited, or reproduced.
