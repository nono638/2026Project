Engineering Notes

Engineering notes · the technical detail

This is the full account of the hardware-stability problems that nearly stopped Experiments 1 and 2, and the engineering layers that eventually made the matrix complete. It’s the technical companion to the plain-English summary on Writeup’s “The technical reality”. Skip it unless you care about Windows kernel bugcheck codes, Ollama internals, or unattended-experiment supervision patterns.

Six BSODs in eleven days

The hardware was an RTX 5090 Laptop GPU on Windows 11. Between 2026-05-17 and 2026-05-19 the machine crashed six times under sustained Ollama batch load. Five distinct bugcheck codes appeared, all rooted in the NVIDIA display driver (nvlddmkm).

Date / timeBugcheckSymptom & phase of run
2026-05-17 22:32 0x00000133 DPC_WATCHDOG_VIOLATION nvlddmkm DPC stayed in a single CPU for too long. First crash — surfaced the pattern.
2026-05-18 02:14 0x0000003B SYSTEM_SERVICE_EXCEPTION Resumed Exp 1 ~32 min after restart. nvlddmkm stack again.
2026-05-18 09:21 0x0000000A IRQL_NOT_LESS_OR_EQUAL Standard hardware-driver fault. Resumed run.
2026-05-18 11:53 0x00000116 VIDEO_TDR_ERROR Windows’ Timeout Detection & Recovery fired when the GPU stopped responding inside an LLM kernel. Config 18/30 (multi_query × qwen3.5:9b @ query 69).
2026-05-18 ??:?? bugcheck not preserved BSOD #5 — minidump was rolled out before triage.
2026-05-19 03:29 silent kill No Python traceback, log just stops mid-row_rest sleep. Config 29/30 (corrective × gemma4:e4b @ query 100). Classic BSOD silhouette.

The NVIDIA developer forum has a long thread documenting similar behaviour on the 5090 family under Ollama load: RTX 5090 total failure / hang / unload in Ollama after a couple of minutes. The consensus across that thread is that this is a driver and firmware-level instability cluster on the 5090 SKU, triggered (not caused) by sustained mixed embed / chat workloads.

Layer 1: software pacing inside the experiment runner

None of these eliminated the BSODs but they cut frequency enough to make progress between crashes. All live in scripts/run_experiment_1.py.

  • Row pace: 0.5 s sleep between every completed (generate + score) row, configurable via --row-pace-s. Inserted between bursts so the GPU could drain its DPC queue before the next embed/chat hit.
  • Periodic mid-config rest: originally a single 10 s sleep every 50 rows. Cut to 3 × 1 s ticks (with an fsynced row_rest_tick heartbeat each second) after BSOD #6 hit mid-sleep — the 10 s monolithic idle was a fat window for ASPM downshift to occur and wasn’t earning anything (GPU sat at 51–56 °C throughout).
  • Inter-config cooldown: 30 s between configs. Gave the driver clean unload time before the next model loaded.
  • Per-row CSV flush + fsync: the runner writes a single row to raw_scores.csv and forces it to disk before moving on. A power loss costs at most one row instead of one config (~25 minutes of work).
  • Per-row JSONL heartbeat: events.jsonl gets a row_done record with the running calls_total and the last in-flight call descriptor. Post-mortem can identify the row and call type the BSOD interrupted.
  • Periodic GPU snapshot: every 10 rows a gpu_snapshot event records temp / utilization / VRAM / power so thermal-correlated crashes can be reconstructed from the trail.

Layer 2: Ollama server tuning

The default Ollama install on Windows runs as a tray app with OLLAMA_MAX_LOADED_MODELS=3 and OLLAMA_NUM_PARALLEL set by the server’s heuristics. The concurrent embedder/chat residency was the allocator-churn regime that correlated with the worst BSOD cluster. The fix is to stop the tray-spawned server and re-launch ollama serve with explicit env vars — the tray ignores env vars set after launch.

scripts/start_ollama_safe.ps1 does this. The vars it sets:

  • OLLAMA_MAX_LOADED_MODELS=1 — forces a clean unload/reload between embedder and chat instead of keeping both resident.
  • OLLAMA_NUM_PARALLEL=1 — our pipeline is serial; this disables Ollama’s per-slot KV duplication.
  • OLLAMA_KEEP_ALIVE=24h — well past any single experiment config; eviction still happens on model-switch (Ollama’s MAX_LOADED_MODELS=1 rule supersedes keep_alive when slots are full).
  • OLLAMA_MAX_QUEUE=512 — explicit so it survives a default change.
  • OLLAMA_MODELS=D:\OllamaModels — the tray app reads this from its own config, not from env vars; passing it explicitly to the replacement ollama serve avoids the fallback to %USERPROFILE%\.ollama\models that otherwise reports every model as 404.

Two settings deliberately not set: OLLAMA_FLASH_ATTENTION (auto-disabled when an embed model is loaded, so a mixed pipeline ignores it anyway) and OLLAMA_KV_CACHE_TYPE (q8_0 KV silently falls back to f16 on archs that don’t support it, masking what’s actually running).

Layer 3: Ollama client tuning

In src/llms/ollama.py:

  • keep_alive="30m" per call. Ollama’s default of 5 minutes let the timer expire mid-config when a slow generation (or judge-side stall) ran long; that forced a full reload on the next call. 30 m safely spans worst-case config duration without locking the GPU when the experiment moves to the next model.
  • num_predict=1024 cap on tokens per generation. Without this, qwen3.5:9b was observed generating runaway responses of 8–17+ minutes on single queries (the regime that drove BSOD #3). Sized from analysis of completed Exp 1 rows across all 5 strategies — 1024 covers >95% of non-degenerate answers while keeping worst-case generation well under the 180 s client timeout.
  • 180 s per-call httpx timeout. The Ollama Python client defaults to no timeout, which is how an 8–17-minute hung chat() happened before BSOD #3. 180 s is 3× the expected worst-case for a 9B model on the 5090 Laptop.
  • Runner-crash recovery wait. experiment_utils.py recognises Ollama’s “model runner has unexpectedly stopped” error and waits 60 s before retrying (the runner process needs ~30–90 s to come back up cleanly after a crash). Normal 2–8 s backoff hits a dead runner and hangs again.

Layer 4: Windows / NVIDIA driver settings

scripts/apply_5090_stability.ps1 (run as Administrator, then reboot):

  • TDR registry keys raised. TdrDelay=60, TdrDdiDelay=60, TdrLevel=3 under HKLM\SYSTEM\CurrentControlSet\Control\GraphicsDrivers. Default is 2 s / 5 s, which is too short for LLM kernels that legitimately hold the GPU through long generations — was triggering 0x116 VIDEO_TDR_ERROR (BSOD #4). Raised to 60 s with full recovery enabled (don’t set TdrLevel=0; that masks bugs instead of surviving them).
  • Hardware-Accelerated GPU Scheduling off. HwSchMode=1. Implicated in 5090 nvlddmkm DPC instability and in the NVIDIA dev forum thread cited above. NVIDIA driver re-installs sometimes flip this back on — check after any driver update.
  • PCIe ASPM disabled. powercfg /setacvalueindex SCHEME_CURRENT 501a4d13-... ee12f906-... 0. ASPM transitions on dGPU laptops are a documented trigger for nvlddmkm stalls, and our per-row pacing was creating idle windows where ASPM could downshift. Plus a forced high-performance power plan so the GPU isn’t throttled mid-call.

Things that didn’t help: a clean NVIDIA driver reinstall (the issue is cross-driver-version), and chasing “cooler temperatures” (the GPU sat at 51–56 °C through the crashed runs — thermal headroom wasn’t the issue).

Layer 5: unattended supervision

The lower four layers reduced BSOD frequency. Layer 5 reduced BSOD cost: when a crash did happen, the run resumed itself rather than waiting for a human to notice and re-launch.

  • Watchdog wrapper. scripts/run_experiment_1_watchdog.py supervises the experiment as a subprocess. On any non-zero exit it re-launches with --resume; the runner’s row-level CSV checkpoint means at most one row is repeated. Exponential backoff caps at 120 s. A zero-progress abort guard stops the loop if two consecutive attempts add no rows — protects against a deterministic Python bug burning through the restart budget. Clean exit at 6,000 rows.
  • Auto-resume after reboot. scripts/install_auto_resume_task.ps1 registers a Windows Task Scheduler entry (RagBench-Experiment1-AutoResume) that fires the watchdog at logon with a 30 s delay. Closes the human-in-loop gap entirely: after a BSOD, log back in, wait ~30 s, the experiment resumes from the last checkpointed row.

With all five layers in place, the final 300 rows of Experiment 1 completed in 46 minutes on a single watchdog attempt, no BSOD, no human intervention — after weeks of fighting that section of the matrix.

Lessons that generalise

  1. Own the unattended-execution loop. Don’t assume the machine will be reliable for the wall-clock duration of an experiment. For multi-day workloads, a watchdog plus auto-resume after reboot is the difference between “completes overnight” and “needs daily intervention.”
  2. Shrink the BSOD blast radius. Per-row fsynced CSV checkpoints + per-row JSONL heartbeats let any post-mortem answer “what was the process doing at the second of death?” This is cheap to add and pays back hugely on every crash.
  3. System-level fixes and software pacing are complements, not substitutes. Either alone was insufficient on this hardware; together they made the run viable.
  4. Default settings on consumer hardware are tuned for desktop interactivity, not batch ML. Windows TDR, GPU scheduling, PCIe ASPM, and Ollama’s tray-app defaults all needed override before a multi-hour Ollama batch could finish reliably.
  5. Forum threads are diagnostic data. The NVIDIA dev forum thread on the 5090 + Ollama pattern was more useful for narrowing the bug hypothesis than any single official source. When bugcheck codes look unfamiliar, search the workload + hardware combination on the appropriate vendor forum before deeper triage.

All five layers above are in the source tree and can be re-applied to a future run: pacing constants in scripts/run_experiment_1.py; Ollama wrapper in src/llms/ollama.py; system mitigations in scripts/apply_5090_stability.ps1 and scripts/start_ollama_safe.ps1; supervisor in scripts/run_experiment_1_watchdog.py + scripts/install_auto_resume_task.ps1.
